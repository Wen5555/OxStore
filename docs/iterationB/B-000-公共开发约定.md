# B-000 挑战B公共开发约定

## 1. 使用依据

业务以[迭代3·产品待办v1.1](https://github.com/Wen5555/OxStore/wiki/迭代3·产品待办)及[需求规格说明书V3](https://github.com/Wen5555/OxStore/wiki/需求规格说明书V3)为准；未替换的基础工程规则沿用T-000，既有拍卖沿用P-A00。接口、字段、错误码和并发方案按本文统一，发生变更须同步前后端与测试。

分工以Sprint Backlog为准，B-026归R1、B-041归配置经理R5。[接口契约.json](B-000-附件/B-000-接口契约.json)提供字段类型、Mock和固定提示，与本文配套使用。它是自定义契约清单，不是OpenAPI。

核对基线：代码main `2c32a880cd4e6ebc7f6717fb5367f6cea60de457`，Wiki `bb0601f29b4fd6c2db4531d1c20037ce18e90476`（2026-11-15）。

## 2. 范围与禁止实现

新一口价必须先加购物车；一批选择建一张多商品多数量整单。下单直接扣剩余可售库存，完成不再扣，取消按快照只回补一次。收藏/购物车服务端持久化且仅本人可操作。

不做：线上支付、真实物流、运费、凭证、售后退款、多商家、详情直接下单、游客车/收藏及登录合并、原地改名称价格图文、商品硬删除、部分流转/取消、自动流转/超时取消、恢复取消订单、取消回车、独立全站总览、强制状态筛选、收藏直接加购/购买、收藏批量管理。不得另加订单金额、件数、明细行数或购物车数量的业务上限。

拍卖是既有独立能力，仅做兼容回归；本契约不为它增加收藏、购物车或五态履约。新车/收藏/结算只接受`FIXED_PRICE`；对`AUCTION`返回已有40908模式错误，不改拍卖规则。

## 4. 通用传输、鉴权与响应

### 4.1 数值、时间和分页

- 新增接口中的业务ID统一十进制字符串，避免JavaScript大整数失真。单个新订单ID和订单号是不同字段，均不可变；订单号用UUID，不与旧意向ID共用空间。
- `quantity/stock`在挑战B接口统一为规范十进制字符串，正整数`^[1-9][0-9]*$`，允许0的更新/库存为`^(0|[1-9][0-9]*)$`。输入负数、小数、空白、科学计数法或JSON number均不写库；数量/库存按各自固定提示。前端用文本输入和精确整数运算，不用`Number`、`parseInt`或带业务max的InputNumber截断。
- 新订单、车、收藏的`unitPrice/lineAmount/totalAmount`用两位小数字符串；后端BigDecimal精确逐行乘整数再求和，不用浮点。原有商品单价规则沿用既有基础需求，不新增订单总金额上限。既有拍卖价格JSON number暂不变，避免破坏其独立客户端。
- 既有商品响应/库存编辑涉及`stock`的地方，同轮升级客户端和DTO接受字符串；不允许一处仍以int反序列化而产生隐藏上限。拍卖库存仍只允许其原有0/1语义。
- 服务端时间沿用BusinessTime和Asia/Shanghai，ISO本地时间`yyyy-MM-dd'T'HH:mm:ss[.SSSSSS]`，客户端时钟不裁定并发。
- 分页沿用PageResponse的`items,page,size,total,pages`，page从1开始；订单/归档默认size=10、最大100（仅分页大小，非记录总量上限），收藏size固定10。排序时间倒序、ID倒序作同时间稳定次序。车返回完整行集合，不分页截断选择。

### 4.2 认证与归属

`Authorization: Bearer <JWT>`；沿用CUSTOMER/SELLER，不接受请求体customerId/sellerId充当身份。所有`/api/me/**`要求CUSTOMER，`/api/admin/**`要求SELLER；后台登录入口保持公开。新增路由必须显式进入SecurityConfig规则，不能依靠当前`anyRequest().permitAll()`兜底。

无客户令牌：40101、“请先登录”；携带无效/过期令牌：40101、“请重新登录”；商家取消缺失或失效令牌：“请先登录后台”。JwtAuthFilter向EntryPoint传递缺失/失效结果，不记录原令牌；权限失败无业务副作用。

越权收藏/车/混合批次：40302、“无权操作”；越权订单：40302、“无权操作该订单”；商家代客户转收藏：40301、“无此权限”。其他角色错误沿用40301。先校验身份、角色、整个批次归属，再返回商品失败明细，不能泄露他人数据后才拒绝。未知ID不等于已证明属于他人，按该操作的缺失行规则处理。

### 4.3 响应与逐项错误

统一`{code,message,data}`，成功code=0；新增写操作成功HTTP200（结算首次建单201）。即使失败也保留JSON结构；成功提示放message；前端直接展示后端message，不按中文判断业务逻辑。B-005给ApiResponse增加message与错误data支持，保留旧方法兼容。

批量失败格式：`{code,message,data:{errors:[{cartItemId,productId,productName,reason,message,availableStock?,requestedQuantity?}]}}`。每项message说明具体商品及原因；完整成功/失败样例见接口JSON的`mocks`。

reason固定`OFFLINE/NOT_FOUND/INSUFFICIENT_STOCK/CART_ITEM_REMOVED/CONFIRMATION_CHANGED`，errors按提交的行顺序返回。缺失商品不伪造名称；顶层概括不能代替逐项message，普通单项错误data可为null。

B-017修改`api/request.ts`：挑战B保留message/data.errors，不被旧code映射覆盖；逐项错误由页面展示，避免重复弹提示。拍卖映射保留。

辅助记录只用于一致性，不新增UI。已删除他人行按墓碑归属拒绝，本人删行才可跳过；未知行结算失败、转收藏按消失处理，不泄露他人信息。Sprint内不清理这些重试判定记录。

## 6. 状态、权限与库存表

新OrderStatus独立于IntentStatus：`PLACED/CONFIRMED/PREPARED/SHIPPED/COMPLETED/CANCELLED`。

| 状态 | 中文 | 商家下一动作 | 客户取消 | 商家取消 |
|---|---|---|---|---|
| PLACED | 客户下单 | CONFIRM → CONFIRMED | 可 | 可 |
| CONFIRMED | 商家确认 | PREPARE → PREPARED | 可 | 可 |
| PREPARED | 备货完成 | SHIP → SHIPPED | 可 | 可 |
| SHIPPED | 开始发货 | COMPLETE → COMPLETED | 不可 | 可 |
| COMPLETED | 交易完成 | 无 | 不可 | 不可 |
| CANCELLED | 已取消 | 无 | 不可重复 | 不可重复 |

订单响应统一返回`allowedActions`，客户为`["CANCEL"]`或`[]`；商家为合法下一动作加`CANCEL`。只是UI提示，服务端每次仍重判。推进请求必须包含expectedStatus；不能把两个并发“下一步”连推两态。商家只能针对当前对应态发固定动作。客户无推进接口。

取消也包含expectedStatus：若并发确认/备货先成功而仍可取消，旧请求可返回40904要求刷新，不把它当终态拒绝；客户刷新后二次明确提交仍可取消。取消先成功其他推进拒绝；SHIPPED客户取消拒绝；SHIPPED商家仍可取消。重复取消返回40911/“订单已取消”，禁止库存二次回补。部分取消字段items/itemIds等一律40004/“不支持部分取消”，不要悄悄忽略后按整单执行。

| 操作 | 库存变化 | 商品状态 |
|---|---|---|
| 建单成功 | 减各明细快照量 | 到0设OFFLINE/AUTO_ZERO |
| 确认/备货/发货/完成 | 不变，不再查是否够量 | 商品下架不影响本单 |
| 成功取消 | 加各明细快照量一次 | 仅原OFFLINE/AUTO_ZERO且本次回补至正数时恢复ONLINE并清原因 |
| 人工改0 | 改为0 | OFFLINE/AUTO_ZERO；若已有MANUAL则保留人工意图 |
| 人工0改正 | 改剩余可售量，不设未完成单下限 | 不自动上架，维持原原因直到显式上架/符合取消恢复条件 |
| 人工下架（包括已自动下架后显式下架） | 不变 | OFFLINE/MANUAL，不因取消恢复 |
| 人工上架 | 库存必须>0 | ONLINE/原因清空；不重新发布 |

库存调整与回补是独立串行操作：先人工设7再取消快照3，最终10；先取消后人工设7最终7。不可把旧初始库存当回补上限。取消无回车、退款、物流回撤或额外凭证。

## 8. 下单事务

1. Q01只校验所选行：空选“请选择商品”，混入他人行整次拒绝，未选失效/缺量不影响；选中失败逐项提示。确认页展示清单、单价、数量和总额，不建单/扣库。
2. Q02先查成功receipt，旧请求直接按重试规则返回，不因车已清空重新建单或报空选。首次请求锁定后再校验归属、商品在售及库存。
3. 确认后锁前数量、身份或单价变化：40913要求重新确认，不按旧清单静默成交；下架/缺量仍返回各自逐项错误。只库存变化且仍足够时可继续。
4. 以最终有效确认及锁定快照为准，已下单数量q、锁定车数量c，清车执行c-q：正数留余数，0删行。锁后加购串行至提交之后，新增量保留；不能按productId盲删整行。锁前加量造成确认失配须先重新确认。
5. 建单/快照/金额、扣库存、零库存下架、余数清车、成功receipt在同一事务提交；任一步失败全部回滚，无“待补清车”或只清车重试。
6. 成功201，展示订单号；响应丢失可查订单历史。有意再买用新确认token和新请求键，允许多笔未完成订单。

## 9. 转收藏事务

1. 二次确认“所选 N 件商品将从购物车移除并加入收藏”，N按行数；默认选在售行，不检查数量够不够库存。
2. 先校验批次归属；本人已删行跳过，全删返回“请选择商品”。任一剩余商品下架/不存在，整批拒绝，逐项提示；已有失效收藏不能豁免在售校验。
3. 去重收藏与整行移车同事务。已有收藏保留时间但仍移车；锁前加量一并移除、不留余数。锁后主动新加购等待提交后建新行。
4. 后取得客户锁的取消收藏可使最终无收藏，但原移动仍成功，车已移除；两请求分别返回当时结果。
5. 同键重试不执行，常规40915“请勿重复操作”；原成功后独立取消再重试，按PB-B15 AC5返回保存的原成功结果，不复活收藏。receipt与favorite_mutation代次用于区分这两种返回。
6. 写收藏/移车失败50001“操作失败，请重试”，业务和receipt一起回滚，同键原body可重试。返回实际移动行集合，不能误删后来新加购行。

## 10. 统一并发、锁定顺序及重试协议

使用数据库事务和行锁。同客户收藏/车/确认/结算/订单命令先锁稳定customer行；读取只返回已提交结果，确认不持锁等待用户点击。

锁顺序：`customer → operation_receipt → order → product(id升序) → cart_item(id升序) → favorite(productId升序)`。只读取定位信息可提前，但锁后必须重验归属和状态。商家订单命令也先锁订单所属customer；库存维护仅锁product，不反向锁customer。拍卖沿用旧锁，持product锁时不得调用新车/收藏/订单命令。

同账号按实际成功提交顺序生效；旧cartItemId改量查不到返回40912，不upsert、不按productId重建，只有主动加购可新建。跨客户锁product后重验库存，避免超卖；死锁/超时整体回滚。并发测试用多连接受控时序。

`Idempotency-Key`用UUID，加购/结算/转收藏必填，按客户+操作类型+键唯一。规范化body计算hash，同键异body返回40916。并发同键等待首事务；业务与成功receipt同事务，失败不留receipt。成功记录持久化，Sprint内不因TTL或重启丢失。

| 操作 | 同键重复 | 独立新操作 |
|---|---|---|
| 加购 | HTTP200、原成功data、“已加入购物车”；不再加量，原行即使后删也不复活 | 新键允许继续加1 |
| 结算 | HTTP409/40909、“订单已提交，请勿重复下单”，data带原orderId/orderNo | 新token+新键允许再买 |
| 转收藏 | 常规40915；独立取消后的重试回原成功结果，见第9节 | 新键重新校验真实当前车行 |
| 收藏PUT/DELETE | 资源语义自然幂等，无需请求键；重复收藏不刷新时间，重复取消“未收藏” | 取消后再收藏是新收藏 |
| 推进/取消 | 不用“重复即成功”掩盖状态冲突；重复动作拒绝 | 合法新状态上的新动作可提交 |

## 11. 新旧一口价隔离与升级

`AuctionSettlementService`会新建旧purchase_intent，`TradeServiceImpl.confirmSuccess/confirmFail`承担拍卖中标旧收尾。不能全局删除这些服务、FROZEN/FAILED枚举、旧History表或旧URL。B-016在商品模式和legacy_closed_at双重校验后隔离：

| 旧能力 | 挑战B处理 |
|---|---|
| POST /api/products/{id}/intents | FIXED_PRICE拒绝40917并提示经购物车下单；拍卖仍按原模式禁止普通意向 |
| 原按商品队列/开始/成功/失败/重新排队 | 一口价已关闭，直调也拒绝40917；拍卖中标的原success/fail仅按旧契约开放 |
| GET /api/me/order-history | 保留既有只读历史用于兼容，不改造成新五态混合列表；新入口使用/me/orders |
| 新旧页面 | 一口价移除购买意向/队列/冻结操作，保留只读归档；拍卖原收尾UI按sellingMode保留 |
| 旧顾客历史 | 既有只读成功失败历史，不在此增加取消按钮 |

升级步骤：停写→备份并核对V6结构/索引/数据计数→V7→V8→核对→部署匹配代码→开放写入。DDL隐式提交，失败停写并按备份恢复。

V8只对FIXED_PRICE的QUEUING/IN_TRANSACTION写关闭标记，保留原status与快照；旧未结束attempt标记关闭而非捏造result。原固定价冻结商品解除冻结、恢复在售，库存不回补；若遇冻结同时stock=0等异常先停下核对，不能跳过库存不变量强行上线。拍卖场次/意向/提醒不动；旧成功失败也不改写。V8重复执行不能二次解冻、回补、复制记录。不要跑旧V4“意向转FAILED”的逻辑代替本次迁移。

新固定价只写shop_order，不写旧intent/trade_attempt、不进入FROZEN；拍卖维持原路径。

## 12. 错误码与固定提示

已有40001/40002/40003、40101/40102、40301/40302、40401～40404、40901～40908、41301/41501/42201/50000保留。新增独立分配如下，业务逻辑按code及reason分支，中文仅用于呈现。

| code | HTTP | 场景 | 提示/结果 |
|---|---|---|---|
| 40004 | 400 | 部分取消 | 不支持部分取消 |
| 40005 | 400 | 空选或转收藏全被删 | 请选择商品 |
| 40405 | 404 | 新订单不存在 | 订单不存在 |
| 40909 | 409 | 同一结算成功后重试 | 订单已提交，请勿重复下单，带原订单定位 |
| 40910 | 409 | 选中商品结算失败 | data.errors逐项，见第4节 |
| 40911 | 409 | 新订单状态不允许 | 已取消/已完成/已开始发货等按场景原文 |
| 40912 | 409 | 旧车行改量 | 该商品已不在购物车，请刷新页面后查看。 |
| 40913 | 409 | 确认快照变化 | 明确提示重新确认，非产品固定原文 |
| 40914 | 409 | 转收藏混合失败 | 逐项商品已下架/商品不存在 |
| 40915 | 409 | 转收藏常规重试 | 请勿重复操作 |
| 40916 | 409 | 同请求键不同body | 明确请求冲突，不写入；工程提示，不冒充产品原文 |
| 40917 | 409 | 旧一口价操作已关闭 | 明确已关闭/需经车下单；工程提示 |
| 50001 | 500 | 转收藏写入或移车失败 | 操作失败，请重试 |

重复推进/expectedStatus不匹配用40904；取消先成功后商家发货用40911/“订单已取消，不可发货”；客户SHIPPED取消用40911/“订单已开始发货，不可取消”；双方COMPLETED取消用“订单已完成，不可取消”；已CANCELLED再次取消用“订单已取消”。认证/归属优先于业务状态，部分取消在允许访问订单之后拒绝。

普通校验/成功提示、空态和确认文案全部使用接口JSON的`fixedMessages`（37项，来自V3 5.3.7）。数量/库存校验用40001；新收藏/加购已下架40901、不存在40401。前端透传原文，不替换为“无货”“缺货”“超限”或“下单历史”。下单有确认步骤；双方取消、清空和转收藏二次确认；取消收藏无需确认，取消原因选填。
