## 2. 部署验证（B-039）

脚本：`scripts/verify_docker_challenge_b.py`。每条路径使用随机命名的独立 Compose 项目、随机端口和新数据卷，只通过 Nginx 的公开端口调用接口，结束后只删除自己创建的项目和卷（`down -v` 只作用于随机项目名）。**镜像是先删除本机同名镜像、再从导出的 `images.tar.gz` 导入的**，导入后镜像 ID 与构建时完全一致，脚本从导出的包目录运行。

证据：`docs/test/evidence/r5-challenge-b-db/container/`（`b039-clean-results.json`、`b039-existing-volume-results.json`、`compose-operations.log`；Compose 输出里的凭据已替换，结果文件不含口令或令牌）。MySQL 为 **8.0.46**。

### 2.3 验证中发现并修复的缺陷

| 缺陷 | 发现方式 | 处理 |

另有验证脚本自身的 3 处问题（检查编号重复、订单详情的 `allowedActions` 客户与商家本就不同被我写成“应相同”、脚本调用升级工具时多了会屏蔽模块搜索路径的参数），都修正后重跑，没有为迎合测试改动应用代码。

## 3. 未覆盖与限制

- 没有真实浏览器 UI 联调与录屏；Mock e2e 不替代。
- 并发规模小（每组最多 8 个并发），不是压力测试；不含 ARM、目标 Linux 主机、公网 HTTPS、长时间运行。
- 升级验证用的是人工构造的数据，**没有对任何真实业务库升级**。
- 拍卖只验证了出价、快照和不能进购物车，没有等待真实结拍；拍卖回归的完整验收是 R2 的 B-035。
- V8 对“卖家手动冻结”的商品转为下架（手动），与 B-000 §11 字面“恢复在售”不一致，仍待 R1 确认；本次升级数据里没有这类商品（`paused_products=0`），该分支只在 B-029 的数据库演练里验证过。
