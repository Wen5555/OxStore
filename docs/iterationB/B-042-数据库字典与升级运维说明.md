## 2. 数值与时间约定（B-003）

- 库存、数量、订单总额、行金额以**规范十进制字符串**存入 `LONGTEXT`，没有 int/long、JS 安全整数或列宽上限。格式由 CHECK 保证：库存 `0` 或无前导零的正整数；数量为正整数；金额恰好两位小数。拒绝负号、小数点（数量）、前导零、空串、空白、科学计数法、尾随换行。
- **在 SQL 里不能对这些列做数值比较或排序**（文本比较会得到错误结果）。需要数值逻辑时，持有行锁后在应用里用 `BigInteger` / `BigDecimal` 运算；只有汇总类查询可显式 `CAST(... AS DECIMAL(65,0))`（本项目验证脚本这样用）。
- 商品单价沿用 `DECIMAL(10,2)`；订单明细的 `unit_price_snapshot` 与确认行的 `unit_price` 同为 `DECIMAL(10,2)`，不承载总额。
- 时间列 `DATETIME(6)`，业务时间为 Asia/Shanghai；订单及取消时间由应用写入，客户端时钟不参与裁定。

## 3. 数据字典

### 3.1 `shop_order`（订单主表，B-001）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT 自增 | 主键 |
| `order_no` | CHAR(36) 唯一 | UUID，CHECK 校验格式；不与旧意向 ID 共用空间 |
| `customer_id` | BIGINT，外键 `customer` | 归属，不可改 |
| `status` | VARCHAR(20) | `PLACED/CONFIRMED/PREPARED/SHIPPED/COMPLETED/CANCELLED`，不复用旧 `FAILED` |
| `total_amount` | LONGTEXT | 两位小数字符串，不可改 |
| `created_at` | DATETIME(6) | 不可改 |
| `cancelled_by` / `cancelled_at` / `cancel_reason` | VARCHAR(20) / DATETIME(6) / VARCHAR(500) | 仅 `CANCELLED` 订单有值；取消时发起方必须是 `CUSTOMER` 或 `SELLER`，取消时间不早于创建时间；非取消订单这三列必须为空 |
| `version` | BIGINT | 仅用于状态并发，任何商品更新都不得据此重算历史快照 |

索引：`uk_shop_order_no`、`idx_shop_order_customer_time (customer_id, created_at, id)`、`idx_shop_order_time (created_at, id)`。
触发器 `trg_shop_order_guard`：订单号、归属、总额、创建时间不可改；`COMPLETED`/`CANCELLED` 订单的状态与取消元数据不可再改。数据库只兜底这些不变量，**跳步、回退、客户无权推进等业务规则由应用状态机判定**。

### 3.2 `order_item`（订单明细快照，B-001）

`id`、`order_id`（外键）、`product_id`（外键）、`product_name_snapshot` VARCHAR(200)、`unit_price_snapshot` DECIMAL(10,2) >0、`quantity_snapshot` LONGTEXT（正整数）、`line_amount_snapshot` LONGTEXT（两位小数）。
唯一键 `uk_order_item_product (order_id, product_id)`：同单同商品一条。触发器 `trg_order_item_immutable`：**全部快照列不可更新**，商品之后改名改价不影响订单。取消回补按 `quantity_snapshot` 进行。

### 3.3 `favorite` 与 `favorite_mutation`（B-002）

- `favorite`：`id`、`customer_id`、`product_id`、`created_at`；`UNIQUE(customer_id, product_id)`；列表索引 `(customer_id, created_at, id)` 支持每页 10 条倒序。重复收藏不更新时间；取消即删除，再收藏是带新时间的新记录。
- `favorite_mutation`：主键 `(customer_id, product_id)`，`operation_seq`、`last_cancel_seq`，CHECK `last_cancel_seq ≥ 0 且 operation_seq ≥ last_cancel_seq`。**须在持有同一客户行锁时维护**。转收藏成功的回执保存当时的代次，之后若 `last_cancel_seq` 更大，说明发生过独立取消，同键重试返回原结果而不重新收藏。

### 3.4 `cart_item` 与 `cart_item_tombstone`（B-002）

- `cart_item`：`id`、`customer_id`、`product_id`、`quantity` LONGTEXT（正整数）、`updated_at`；`UNIQUE(customer_id, product_id)`。数量 0 由**删除行**表达，数据库拒绝 0、负数、小数。
- `cart_item_tombstone`：`cart_item_id` 唯一、`customer_id`、`product_id`、`removed_at`；无外键。删行、清空、转收藏、结算清车**必须在同一事务写墓碑**，旧 `cartItemId` 才能区分“本人已删”“他人的行”“从未存在”。MySQL 8 的自增值持久化，已删行 ID 不复用。

### 3.5 `checkout_confirmation` 与 `checkout_confirmation_item`（B-003）

确认快照，不建订单、不扣库存。主表 `token` CHAR(36) 唯一、`customer_id`、`total_amount`、`digest` CHAR(64)、`created_at`；明细 `confirmation_id`、`cart_item_id`、`product_id`、`unit_price`、`quantity`，`UNIQUE(confirmation_id, cart_item_id)`。`cart_item_id` 不加外键，车行之后可能被删而快照仍须保留。

### 3.6 `operation_receipt`（幂等回执，B-003）

`customer_id`、`operation_type`（`CART_ADD/CHECKOUT/MOVE_TO_FAVORITES`）、`request_key` CHAR(36)、`request_hash` CHAR(64)、`result_payload` LONGTEXT（CHECK 必须是合法 JSON）、`completed_at`。`UNIQUE(customer_id, operation_type, request_key)`。**只落成功结果，必须与业务变更在同一事务提交**，失败不留回执；不存 JWT 或口令。

### 3.7 既有表的增量

| 表.列 | 变化 |
|---|---|
| `product.stock` | `INT` → `LONGTEXT`；CHECK 替换为规范非负整数；拍卖商品仍只允许 `'0'`/`'1'` |
| `product.offline_reason` | 新增，`AUTO_ZERO`/`MANUAL`/NULL；V7 只给**一口价**的 OFFLINE 商品初始化（库存 0 → `AUTO_ZERO`，否则 `MANUAL`），拍卖商品不动 |
| `purchase_intent.legacy_closed_at` / `legacy_close_reason` | V8 写入；CHECK 要求同时为空或同时有值；索引 `idx_intent_legacy_customer`、`idx_intent_legacy_product` |
| `trade_attempt.legacy_closed_at` | V8 对被关闭意向的**未结束**尝试写入；CHECK 要求其 `finished_at/result/fail_action` 为空（不捏造结果） |

## 4. 锁与事务使用约定（给 R1/R4）

按 B-000 第 10 节的顺序加锁：`customer → operation_receipt → shop_order → product（id 升序）→ cart_item（id 升序）→ favorite（product_id 升序）`。仓库已提供对应 `FOR UPDATE` 查询（`CustomerRepository.findByIdForUpdate`、`ProductRepository.findByIdForUpdate`、`CartItemRepository.findAllByIdForUpdate` 等）。数据库层面可用下面的查询自查：

```sql
-- 库存账：初始量减有效订单量等于当前库存（仅对未被人工改过库存的商品成立）
SELECT i.product_id, SUM(CAST(i.quantity_snapshot AS DECIMAL(65,0))) AS sold
FROM order_item i JOIN shop_order o ON o.id = i.order_id
WHERE o.status <> 'CANCELLED' GROUP BY i.product_id;

-- 车行与墓碑不应重叠
SELECT COUNT(*) FROM cart_item c JOIN cart_item_tombstone t ON t.cart_item_id = c.id;

-- 已下架原因分布
SELECT status, offline_reason, COUNT(*) FROM product GROUP BY status, offline_reason;
```

## 5. 升级运维

### 5.1 步骤

1. **停写**：停止应用（或至少停止后端容器），确认没有进行中的交易。
2. **备份并核对**：升级工具会先做 `mysqldump --single-transaction --routines --triggers` 并写入 `.work/db-backups/`（已被 Git 忽略；备份含个人信息，放受控磁盘，不提交）。工具拒绝空备份，并输出备份大小与 SHA-256。
3. **运行工具**（容器须提供 `MYSQL_ROOT_PASSWORD`，容器名、库名按实际替换，示例名不是实际环境）：
   ```powershell
   python -X utf8 scripts/migrate_challenge_b.py --container oxstore-mysql --database shop
   ```
4. **核对**：工具输出 `phase_before`、`applied`、`phase_after` 与 V8 的四个计数（`closed_intents`、`closed_attempts`、`unfrozen_products`、`paused_products`）。与停写前的意向/尝试/商品状态分布对照；`phase_after` 必须是 `challenge_b`。
5. **部署匹配的代码**（后端镜像含 V7 之后的实体）。注意后端默认 `ddl-auto=none`，**启动时不会校验表结构**：代码与库不匹配时，要到第一次查询才报错（例如 `Unknown column 'offline_reason'`），健康检查随之失败。
6. **开放写入**。

### 5.2 V8 对数据的处理（只改标记，不改原状态）

| 数据 | 处理 |
|---|---|
| 一口价、状态为 `QUEUING`/`IN_TRANSACTION` 的意向 | 写关闭时间与原因 `FIXED_PRICE_CHALLENGE_B`；**原状态与快照不变，不转为 `CANCELLED`/`FAILED`** |
| 上述意向未结束的交易尝试 | 写关闭时间；结果仍为空 |
| 一口价、`FROZEN` 且冻结来源 `TRADE` 的商品 | 恢复 `ONLINE`，库存不回补 |
| 一口价、`FROZEN` 且冻结来源 `MANUAL` 的商品 | 转为 `OFFLINE` + `offline_reason=MANUAL`（新模型没有冻结态，卖家有意暂停的商品不应被擅自上架）。**这一条与 B-000 §11 的字面“恢复在售”不同，待 R1 确认**；若要按字面处理，只改 V8 中对应的一条 UPDATE |
| 拍卖商品、场次、出价、提醒；已成功/失败的旧意向与尝试 | 不动 |

旧 V4 把排队意向转为 `FAILED` 的规则**只用于五表基线（`legacy`）的首次升级**，不用于 V8。

### 5.3 异常与恢复

- **识别阶段拒绝**：结构缺表或缺列时直接拒绝，不备份、不改动。先核对结构，必要时从备份恢复到临时库对照，不要强行迁移。
- **V8 前置检查停止**（任何变更之前）：一口价商品处于 `FROZEN` 且库存为 `0`；冻结来源缺失或未知；已有意向带有非本次的关闭原因。工具会输出 `failed_at`、错误信息和 `recovery` 提示，备份保留。此时 **V7 已完成并保留**（DDL 隐式提交，不能整体回滚），V8 没有改任何数据。处理异常数据后重新运行工具即可。
- **V7 中断**：重新运行工具；V7 逐项检查是否已完成，缺少的 CHECK、列和表会补齐。
- **不要**假定 DDL 事务能自动整体回滚。要回到升级前，停写并恢复**已演练过**的备份；演练应先恢复到独立空库，不要直接对业务库试。
- **不要**用旧版程序继续写入已升级的库。

### 5.4 Docker Compose 部署

- 空数据卷首次启动会导入随包 `database/schema.sql`（直接得到 21 张表）；**已存在的数据卷不会重放初始化脚本**，更换镜像版本或 `docker compose up` 都**不会**升级表。已验证：新镜像连接未升级的旧卷时后端无法健康启动（首个查询报 `Unknown column 'offline_reason'`），且 12 张表保持原样。
- 已有数据卷必须先按 5.1 显式升级，再换新镜像启动。具体命令与验证记录见 [B-038/B-039 记录](B-038-039-集成候选与部署验证.md)。
- 不要对真实数据卷执行 `docker compose down -v`；验证脚本只对自己创建的随机项目执行。

## 7. 限制

- 并发验证是小规模（单实例、每组最多 8 个并发），不是压力测试，也不是并发正确性的证明；不含 ARM、目标 Linux 主机和公网部署。
- 升级演练使用人工构造的夹具，不是真实业务库；**没有对任何真实业务库执行过升级**。
- 本文的字段说明随 V7/V8；后续 DDL 改动由 R5 同步更新本文。
