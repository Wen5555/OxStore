# B-028 真实 MySQL 约束与事务辅助验证（R5）

范围：B-000 第 8～10 节的结算、取消、转收藏和库存规则在真实 MySQL 上的行为。这是 R5 的数据库层验证，**不替代 R2 的独立业务验收**（B-032/B-033/B-034）。

## 2. 方法

- 运行打包后的后端 JAR（`--spring.jpa.hibernate.ddl-auto=validate`，所以同时验证了 V7 之后后端能在真实 MySQL 上启动）。
- 真实 HTTP 调用；并发用线程栅栏让请求同时发出，不靠人工连点。
- 所有断言通过**独立的 mysql 客户端连接**读库，不经过应用。
- 故障注入用数据库触发器在指定写入点 `SIGNAL`，不改应用代码。
- 数据库来源：`--db docker`（本次运行创建并删除的 `mysql:8.0.46` 容器）或 `--db local`（临时目录里的一次性 mysqld，随机回环端口，绝不连接已安装的 MySQL 服务）。运行后已按 PID 确认进程消失、临时目录已删除。
- 检查失败只记录、不中断，一次运行能看到全部问题。

## 3. 复现

```bash
mvn -B -ntp -f backend/pom.xml -DskipTests package
python scripts/verify_b028_transactions.py --db docker
```

目标环境用 `--db docker`（默认，镜像 `mysql:8.0.46`）。没有 Docker 时可用 `--db local --mysql-bin "<MySQL bin 目录>"`。结果写入 `docs/test/evidence/r5-challenge-b-db/`。

## 5. 本次发现的问题

- **应用缺陷：无。** 所有失败项（共 3 项，运行过程中出现）都是验证脚本自身的错误，已修正后重跑：Python `Decimal` 默认 28 位精度导致 30 位库存的期望值被舍入（S13、S17）；转收藏回执计数把加购产生的 `CART_ADD` 回执也算进去了（S10a）。
- 因此没有需要转交 R1/R4 的缺陷。这不等于没有缺陷，只代表这些检查没有发现。

## 6. 未覆盖与限制（不得当作已验证）

- 并发规模小：单个应用实例，每组最多 8 个并发请求，重复数轮；没有压力、长时间或多实例测试，也不是性能结论（B-000 明确不设性能数值门槛）。
- 竞争类结果取决于调度，通过只说明这几组时序下没出错，不是并发正确性的证明。8.0.46 一次运行中 S06 发货赢 6 次、取消赢 2 次，S07 取消赢 4 次、完成赢 2 次，两个分支都出现过，说明竞争确实打到了；S05 三轮分别是商家、商家、客户取消获胜。9.5.0 的分布不同（5/3、4/2），说明结果随调度变化。
- 故障注入只覆盖了选定的写入点，没有覆盖连接中断、锁等待超时、数据库重启。
- 没有验证旧库升级与重启持久化演练（B-029）和部署（B-039）。
- 没有覆盖前端；真实前后端主链路由 R2 的 B-036 验收。
- R1 的 `ChallengeBCheckoutIntegrationTest` 等是开发自测，本验证与它们相互独立，但没有逐项比对覆盖重叠。
