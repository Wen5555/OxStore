# OxStore 后端最小修改计划（对齐需求 V1）

**制定日期：**2026-09-30  
**目标：**修复已确认的需求差距，并保留现有单卖家、单商品、Spring Boot + JPA + MySQL 的实现路线。**本文是实施计划，不代表代码已经修改或测试已经完成。**

依据：[需求规格说明书 V1](https://github.com/Wen5555/OxStore/wiki/%E9%9C%80%E6%B1%82%E8%A7%84%E6%A0%BC%E8%AF%B4%E6%98%8E%E4%B9%A6V1)、[本次后端审查报告](./OxStore-后端需求符合性审查.md)；事务与锁的具体用法参考 [Spring Data JPA 官方事务说明](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html)及[锁说明](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html)。

## 一、先定范围：只解决三个问题

1. **需求验收前必修：失败后重排不能抹掉提交时间与失败记录**（S-010、S-012）。
2. **需求验收前必修：后台能读取已有的关键时间，并保留交易失败处理时间**（S-004、S-010、S-012）。
3. **若对外部署则上线前必修：移除可预测的初始管理员密码与 JWT 默认密钥。**纯本地隔离演示可以先做前两项，但不能把演示配置直接用于公网。

**不在本轮顺手重构：**商品/意向状态机、现有 18 个 HTTP 方法+路径组合、JWT 技术选型、前端页面、分页实现、全量口令查找、图片存储架构。性能及孤儿图片问题进入第六节的验证门槛，未证实超标前不改。电话首位必须为 `1` 与需求“11 位数字”的差异，先由需求负责人确认是否仅接收大陆手机号；不自行改变规则。

## 二、准备与基线（动代码前）

- [ ] 在**有版本记录的代码副本/分支**上工作。本机当前 `OxStore-main/` 没有 `.git`，不能直接把本地文件认作附件所说的 `b641f11`；先确认拟修改的实际版本。
- [ ] 记录现有 35 项领域单测结果，并另在可用 MySQL 8 测试环境复现最小场景：A 提交 → A 开始交易 → A 失败并 REQUEUE → A 再次进入交易。记录当前 `purchase_intent.submitted_at`、`processed_at` 的变化，作为回归对照。
- [ ] 如已有业务数据，**先备份数据库并在副本执行迁移**；新库初始化脚本和已有库升级脚本分开。`schema.sql` 的 `CREATE TABLE IF NOT EXISTS` **不会修改现有表**，Docker 的 `/docker-entrypoint-initdb.d` 也只在数据卷首次初始化时运行。
- [ ] 迁移前检查是否存在 `IN_TRANSACTION` 的旧意向：优先在旧版本中处理完该笔交易再升级。否则新版本找不到对应的未结束交易尝试，必须针对这笔存量交易制定一次性兼容处理，且不得捏造未知的开始时间。
- [ ] 确认约定：保留买家**首次提交时间**；重新排队仅改变排队顺序；一次交易失败记一条不可覆盖记录；当前 API 的原有字段不删除、不改含义。

## 三、第一阶段：保住原提交时间、正确重排、保存失败过程

### 3.1 最小数据结构

- [ ] 在 `purchase_intent` 增加 **`queue_seq BIGINT`**：每个商品下按递增序号排队；原 `submitted_at` 从此作为**首次提交时间**，REQUEUE 不再修改。对 `(product_id, queue_seq)` 加唯一约束，已撤销、已失败意向的序号也保留，不复用旧号。
- [ ] 只增加一张**交易尝试表**（例如 `trade_attempt`）：`id`、`intent_id`、`started_at`、`finished_at`、`result`（SUCCESS / FAILED）、`fail_action`（REQUEUE / DISCARD，非失败时为空）。每次进入交易产生一条记录；确认结果时结束该条记录；自动递补或单人立即再次进入交易时产生**新记录**。这张表只承担交易历史，不做通用审计系统。
- [ ] 更新新库的 `backend/src/main/resources/db/schema.sql`；如存在已部署数据库，再提供**一次性迁移 SQL**：先增加可空列、按现有 `(submitted_at, id)` 次序为各商品的旧意向回填 `queue_seq`、确认无空值/重复后再加非空和唯一约束，最后建交易尝试表。**旧数据已被覆盖的原始提交时间及失败尝试无法凭迁移脚本还原；不得伪造历史记录。**

### 3.2 精确代码修改点

- [ ] `entity/PurchaseIntent.java`：创建意向时保存首次提交时间和队列序号；`requeue()` 只更新队列序号、状态、处理时间并使旧口令失效，**不动 `submittedAt`**。
- [ ] `repository/IntentRepository.java`：`findQueue`、`findQueueForUpdate` 按 `queueSeq` 排序；历史意向仍按原始 `submittedAt, id` 排序。增加取当前商品最大序号的方法；序号分配必须在**锁住活跃商品行之后**进行，避免并发读到相同的下一位次。
- [ ] `service/IntentServiceImpl.java`：在原有商品行锁事务内为首次提交分配新序号，保留提交成功返回的队列位次行为。
- [ ] `service/TradeServiceImpl.java`：沿用现有 `@Transactional` 和商品行锁；开始交易/自动递补时写入交易尝试，成功/失败时结束当前尝试，并在失败 REQUEUE 时分配**比该商品历史最大 `queueSeq` 更大的序号**。避免在取得商品锁**之前**建立可能陈旧的查询快照；必要时调整当前 `loadIntent()` 与 `lockActiveProduct()` 的顺序，并用 MySQL 集成测试验证。当前意向、商品、下一位意向及交易尝试必须**同一事务提交或一起回滚**。
- [ ] 加一个简洁的 `TradeAttempt` 实体/Repository 即可；**不增加**消息队列、事件总线、Redis、通用状态机框架。

### 3.3 本阶段完成条件

- [ ] 两人 A→B 排队：A 失败 REQUEUE 后 B 自动进入交易，A 排在剩余买家之后；A 原始 `submittedAt` 不变、旧口令失效，后台可读到 A 第一次失败的时间与处理选择。
- [ ] 单人 A 失败 REQUEUE：同一事务内 A 再进入交易，商品仍为交易冻结；A 的第一次失败记录与第二次交易记录**同时存在**，不会因为重进交易覆盖前一次结果。
- [ ] A 连续两次失败后最终成功：三次尝试按时间可查，前两次失败结果及时间未丢；成功后其余排队意向 UNSOLD，全部相关旧口令失效。
- [ ] 两个提交请求并发：都成功接收时序号不重复、不丢单；两个开始交易请求并发时最多一个 `IN_TRANSACTION`。以 MySQL 8 实测，而不是只靠 Mock 断言。

## 四、第二阶段：让后台拿到可验收的时间证据

- [ ] `dto/response/ProductResponse.java` 增加已有实体的 `statusUpdatedAt`，使当前商品接口可显示**最近一次**状态变化时间；保留现有 `publishedAt`、`soldAt`。这是追加字段，不移除旧字段，也不必新建一套商品 DTO。
- [ ] `dto/response/IntentResponse.java` 增加已有实体的 `processedAt`，历史意向详情可显示最终处理时间；`submittedAt` 始终表示首次提交时间。
- [ ] `dto/response/ProductHistoryDetail.java` 的历史详情响应**追加**交易尝试列表（按 `intentId` 关联，包含开始、结束、结果及失败选择）；在 `ProductServiceImpl.getHistoryDetail()` 中查询该商品意向的尝试记录。保留原有 `product`、`intents` 字段，降低前端联调成本。
- [ ] 通过后台接口核验：商品发布/最近状态更新时间、成交时间；意向首次提交/最终处理时间；曾 REQUEUE 的失败处理时间和结果。**只在确认验收确实要求“历次手动冻结/解冻均有独立历史”时**，再补一张小型商品状态事件表；不要预先铺设通用操作日志框架。当前实体的 `statusUpdatedAt` 只代表最近一次状态更新，不能冒充完整事件历史。

## 五、第三阶段：对外部署前收紧默认认证

- [ ] `application.yml` 不再内置可公开推测的 JWT 签名密钥；从环境变量读取且缺失时拒绝启动。`DataInitializer.java` 不再写死初始管理员密码：仅在**首次创建管理员**时从环境变量读取，并校验强度；已有管理员记录和已修改密码在重启时不得被重置。
- [ ] `docker-compose.yml` 使用必须显式提供的环境变量传入 JWT 密钥、初始管理员密码与数据库密码；提交**只有变量名和填写说明**的样例配置，绝不提交真实密钥或密码。README 写清如何在本地配置环境变量、首次登录后修改密码。
- [ ] 在测试库验证：缺少必填密钥启动失败；随机密钥及初始密码可登录；改密后旧密码不能登录；重启后新密码保留；旧密钥签发的 JWT 在换钥后失效。若某实例已使用公开默认密钥，对外部署时**必须换钥**，不能只修改账号密码。

> 这一阶段是**发布门槛**，不是为了通过本地功能演示而添加复杂的权限系统。无需在 V1 增加 OAuth、角色体系或 Token 黑名单。

## 六、验证与交付顺序

- [ ] **先验证业务闭环：**新增 Service/Repository 层 MySQL 集成测试覆盖第三节四组场景，以及撤销、成功下架、非法状态下事务回滚；确保原 35 项单测仍通过。
- [ ] **再验证 API：**使用既有端点跑发布→多人排队→失败作废/重排→递补→成交→历史详情，核对兼容的 JSON 字段、口令失效、后台鉴权和错误状态码；不新增无必要的公开端点。
- [ ] **最后做非功能取样：**以预期数据量测凭码查询是否 ≤2 秒、历史列表是否可接受；若**实测超标**，再单独开任务优化 token 定位或数据库分页。图片 409 后孤儿文件先复现并量化，再决定是否补简单清理逻辑；这两项**不阻塞本轮业务缺口修复**。
- [ ] 如有旧库：在副本执行迁移、验收后安排部署；部署前备份与核对行数/唯一约束，部署后抽查历史详情。**回退优先回退应用并保留新增字段/表，不直接删除已写入的交易历史；数据异常时依据备份恢复。**

## 七、明确的停手标准

当 **首次提交时间不再随 REQUEUE 改动、每次失败有可读的结果与处理时间、后台返回现有关键时间、对外部署没有默认可预测密钥/密码、核心回归测试通过**，本轮即完成。其余建议记录为后续任务，**不要顺手重写整个后端**。

**特别说明：**计划涉及数据库结构，不应直接对当前真实数据运行未经验证的迁移；已有历史若早已被覆盖，只能如实说明不可恢复的时间范围。
