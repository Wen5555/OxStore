## 结论

**后端已具备 MVP 的主要业务链路，但不能认定“需求 V1 全部满足/已完成验收”。**商品发布与展示、意向排队及口令码管理、卖家认证、冻结/解冻、队首交易、失败递补、成交下架和历史查询都有对应实现。主要缺口是 **REQUEUE 会抹掉失败记录与原提交时间**、**关键时间戳虽有持久化但未完整提供给后台 API**；默认部署认证配置存在**高风险**。响应时间、并发及重启持久化目前没有足够测试证据。

## 优先处理的发现

### P0 — 默认部署可预测认证凭据与签名密钥

`DataInitializer.java:11-35` 固定生成初始管理员账号/密码；`application.yml:28-33` 把 JWT 签名密钥硬编码为公开字符串；`docker-compose.yml:19-28` 没有覆盖 JWT 密钥，数据库也使用固定密码。若按当前 Compose **原样对外部署**，默认凭据可直接登录，公开密钥可用于伪造后台 JWT；这不满足“未登录用户不得访问后台”的实际安全目标。**建议：**JWT 密钥与初始管理员密码均从必填环境变量注入，启动时拒绝缺省/示例值；已部署环境应轮换密钥并修改初始密码。开发示例与真实部署配置分开。

### P1 — 失败重排会丢失交易历史

`PurchaseIntent.requeue()` 同行覆盖提交时间、处理时间和失败状态；之后 `enterTrade()` 又覆盖处理时间（`PurchaseIntent.java:92-97`）。**建议：**保留原始 `submittedAt` 不变，增加 `queuedAt` 或递增排队序号供重排排序；另建交易尝试/状态事件表保存每次开始、失败动作、处理时间、后续结果，或等效的不可覆盖历史。历史查询返回这些记录。测试“单人 REQUEUE→再次失败/成功”及“多人 REQUEUE→成交后历史”应核验所有失败事件仍可见。

### P1 — 后台关键时间戳 API 不完整

实体虽存 `Product.statusUpdatedAt`、`PurchaseIntent.processedAt`，但当前/历史响应 DTO 未暴露；且单个 `statusUpdatedAt` 无法同时还原历次冻结、解冻和交易开始时间。**建议：**至少将最近状态更新时间与意向处理时间加入后台专用 DTO；若验收要求“历次关键操作时间完整记录”，使用不可覆盖的事件记录而不是仅靠最新时间戳。买家商品 DTO 不必因此暴露后台专有字段。

### P2 — 口令码查询规模与图片上传回滚

`findWithToken()` 读出所有有效码，`resolveToken()` 逐个 BCrypt 校验，复杂度随有效意向数线性增长；需要生产相近数据量下的耗时实测。可采用“随机公开查找 ID + 独立高熵 secret 哈希校验”的组合，确保数据库索引定位同时避免可预测访问。图片先落盘后检查活跃商品，建议先校验/锁定业务条件，再存临时文件，数据库提交成功后定稿，失败清理临时文件。

## 验证边界与建议验收用例

1. **已跑通：**35 个领域层单测（状态迁移及口令码生成/匹配）；不是接口测试。
2. **未验证：**本地没有成功运行 MySQL/HTTP 实测；当前进程无可用的 Docker daemon 权限，未主动启动/改动用户数据库。附件记载的 Windows+MySQL 手工测试属于**先前评审证据**，不能替代本次独立验证。
3. **优先补测：**REQUEUE 多次后的历史状态、原提交时间和处理时间；连续 30～100 个有效口令下查询耗时；商品/意向并发提交与事务冲突；图片上传后发布 409 的孤儿文件；Compose 重启后状态及密码保持；默认密钥/凭据被拒绝启动。
4. **界面及性能：**“交易中/无商品”的文案、按钮禁用、前端校验、页面 ≤3 秒、图片上传 ≤10 秒，均不能单靠本次后端静态审查判定。

**与附件结论的差别：**“全部条款已对齐”“16 个接口”的表述过强。现有 7 个 Controller 实际有 **18 个 HTTP 方法+路径组合**（含图片 GET）：买家 5、图片 1、认证 2、后台商品 6、后台队列 1、交易 3。数量不影响功能，但建议修正评审成果说明，并将手工验证与自动化/性能/并发验证明确区分。
